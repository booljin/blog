## s2.1 一个承诺的兑现
在 [第五篇](./gaia-05.md) 开头，笔者曾说过，事件驱动是理解整个 Gaia framework 的钥匙，并许诺未来单独成文。到了兑现的时候，笔者发现 **“事件驱动”** 这四个字单独拎出来讲，容易变成教科书式的定义，索然无味。
<!--more-->

真正让笔者觉得这件事可以说透的，是把它和 **“无状态”** 绑在一起讲。在笔者眼里，这两者从来不是两个独立的设计原则——事件驱动是外，无状态是内。外层决定基本形态，内层决定能力上限。

为了把这个抽象组合说清楚，笔者打算借用你我都熟悉的日常场景：政府办事大厅。

## s2.2 一个类比：办事大厅里的三道工序
假设你去一个办事大厅办某项业务。进大门，取号，然后依次经过三个窗口：A窗口交材料，B窗口审核，C窗口领证。每个窗口后面坐着一个工作人员，你办完一道，去下一道。

这个场景看起来平淡无奇，但如果你仔细看它的运转方式，会发现它和很多软件系统的设计理念惊人地一致。

### s2.2.1 每一次窗口叫号都是一个“事件”
你取号之后坐在等候区，眼睛盯着叫号屏幕。屏幕亮了，显示你的号码和窗口号——“请A003号到3号窗口”。你起身走过去，把材料递给工作人员。

这个“叫号”的动作，在技术世界里就叫事件。

它有几个鲜明的特征：它只传达一个信息——“现在轮到你了”；它不关心你之前排了多久、之后要去哪里；它也不关心这个窗口上一个处理的是谁。事件本身没有记忆，来了就是来了，处理完就消失了。

办事大厅不做预判，它只是等着叫号这件事自然发生，然后响应它。这正是事件驱动的第一层含义：你不是主动去问“有没有事发生”（轮询），而是等事情发生了，它主动来找你。主动权在事件源（你）手里，不在调用者（窗口办事人员）手里。

### s2.2.2 窗口工作人员不记事儿
你走到窗口前，递上材料。工作人员接过来，看一眼，该盖章盖章，该签字签字，然后递还给你，说：“好了，去下一个窗口。”

这个工作人员有一个很有意思的特点——他完全不记得你。你走了之后，他不会保留任何关于你的印象。你问他“刚才那个人办的是什么业务”，他答不上来。他手里没有账本、没有便签、没有任何历史记录。他只负责一件事：你给他一份材料，他按照规则处理完，交还给你。

这种特性，就叫 **无状态**。

因为*无状态*，这个窗口可以换任何人来坐。今天甲坐在这里，明天乙坐在这里，只要知道规则，谁都能干，结果都一样。窗口工作人员之间不需要同步，不需要沟通，因为每个工作人员都不依赖别人，也不依赖过去，谁拿到材料谁处理，处理完就完事。

### s2.2.3 材料在流转，窗口不保留
你从 A窗口 拿到盖好章的材料，走到 B窗口。B窗口 的工作人员接过材料，不看 A窗口 的人，只看材料上的章。材料合格，就继续处理；不合格，退回。整个过程中，材料是唯一的信息载体。

这里有一个容易被忽略的关键点：材料在你手里流转，而不是在窗口之间流转。你拿着材料从一个窗口到另一个窗口，窗口本身不保留任何状态。

这和很多软件系统的设计恰好相反——很多系统默认“状态应该留在服务器上”，而这里的状态跟着请求走。请求（也就是你本人）携带了所有必要的信息，每个处理节点只负责处理当前这一步。处理完了，所有东西都交还给请求本身。

这也是无状态的一种体现。状态不是不存在，而是被装在请求里流动，而不是沉淀在处理节点上。

当前很多大模型推理任务本质上都是这样的。上下文由客户端自己持有，服务器原则上不会持有任何会话有关内容。做到极致，就像Cursor那样：你的每次请求，都可能路由到不同的大模型上，一会儿Codex，一会儿Opus。

#### 一个补充
有些业务特别复杂，窗口人员会手下你的材料，让你三天后过来取。下班交接时，会有专门的工作人员将这些留下来的材料带走，交给后台工作人员处理。窗口人员手下材料，并不会是他的工作变得更复杂，因为他不需要跟踪处理。所有的信息，都在，且仅在材料中。任何一个后台工作人员都基于眼前的这一份材料，以及规定的流程进行处理，在自己的职权范围内，不需要和其他任何人沟通，处理完再将材料交给下一道工序。

所以，临时状态是可能短暂存在于服务器上的，具体表现就是 Gaia 中多次提到的 **“会话 Session”**。但 *状态被装在请求里流动，而不是沉淀在处理节点上* 仍然是一条基本的原则

### s2.2.4 队伍本身是有序的
办事大厅还有一个不言自明的特征：排队。没有人会插队，也没有人会同时站在两个窗口前。每个办事的人，在任何一个时刻只占用一个窗口。

这个秩序不是靠复杂的管理系统维持的，而是靠物理规律和人的常识共同保证的。一个人不可能同时出现在两个地方，所以就不会有两个窗口同时处理同一个人的情况。一个窗口一次只能接待一个人，所以每个窗口的办事流程天然就是串行的。

这就是入口串行化。它不是在处理完之后再去做冲突检测，而是从入口处就保证了秩序。想插队？门都没有。

## s2.3 Gaia 怎么运用 事件驱动 和 无状态
如果你已经理解了办事大厅的组织方式，现在就可以回过头来看看 Gaia framework 怎么和上面的例子对应。办事大厅的 *事件* 是外，由外部触发了工作人员的响应，而 *工作人员不需要记事* 是内，这条内部流程设计铁律决定了办事大厅可以不依赖于任何具体办事人员，能高效稳定的提供标准服务。

第一层：事件源——谁在叫号
办事大厅的叫号屏幕是事件源。在Gaia里，外部事件源有三个：Equipment（机台）、Edge（边缘节点）、Frontend（前端）。除此之外，还有内部事件源，如定时器等。它们各自产生不同类型的事件，各自触发不同的处理流程。

但这不是说所有事件平起平坐。不同事件有不同的优先级，这件事笔者会在下一篇番外里展开讲。在本文里，我们只关注“事件进来之后怎么处理”这个通用骨架。这里只聚焦于 Frontend（前端）的请求事件，因为它本质上是人机交互，和 Equipment / Edge（设备物理事件），以及 定时器（系统日常事件）性质不同。

第二层：无状态处理——窗口工作人员对应API Handler
办事大厅的窗口工作人员不记事儿，谁坐这个位置都能干。Gaia里对应的是 API Handler。

每一个 API Handler 接收请求、产出响应，不依赖全局变量、不依赖上一次调用的状态。正因为它无状态，才能被丢进 API专属工作线程池 里任意并发——四个线程同时跑八个 Handler，谁也不会踩到谁的脚。

第三层：状态跟着请求走——材料对应Context
在办事大厅里，材料在你手里流转，窗口不留存。Gaia里对应的是 ApiContext。

每个请求携带自己的 Context，包括 session_id、connection_id、以及一个 Notify 收集器。Handler 在处理过程中，把需要产生的结果写入 Context，而不是写到某个全局变量里。处理完后，Context 继续流转到下一个环节。

状态跟着请求走，而不是沉淀在服务器上。这也是无状态架构的一个核心特征。

<span id="gaia-s02-lock"></span>
第四层：入口串行化——排队对应Gateway门禁
办事大厅里，一个人一次只能占用一个窗口。Gaia里对应的是 Gateway 配合 assistant 线程管理的 session_map。

前端每发一条请求，Gateway 会先问 assistant：这个 connection 当前有没有 pending 的 session？如果有，直接拒绝，不放行。只有 session 为空时，才接受新请求。这不是事后去重，而是事前门禁。

讲到这里，可能有些读者会想：办事大厅是串行的，但软件系统追求高并发，这不是矛盾吗？笔者的判断是：单个用户的串行化和系统整体的高并发是两个层面的问题。有关这个方面的更详细的讨论，笔者计划单独写一篇文章。

## s2.4 一个补充：事件驱动 与 顺序驱动 的关系
把办事大厅的结构看清楚之后，笔者想额外说一个容易被误解的点。

很多人认为 **事件驱动** 和 **顺序驱动** 是两种完全不同的编程范式，是二选一的关系。但笔者认为这是一个常见的误解。两者并非对立，而是不同尺度上的分工。

事件驱动解决的是“触发器从哪里来”的问题。在办事大厅里，叫号屏幕亮起是一个触发器，有人推门进来是一个触发器，工作人员按铃叫下一个也是一个触发器。系统有多个触发器，不只有一个入口。

但当任何一个触发器被触发并进入处理流程后，内部的所有逻辑仍然是顺序的——取号、排队、交材料、审核、领证，每一步都有先后顺序。即使在流程中跨越了多个后台工作人员（对应软件里的多个线程），时序也是确定的、可预测的。异步只是改变了执行者，没有改变执行的顺序。

事件驱动管的是谁触发，顺序驱动管的是触发后怎么做。两者不是替代关系，是层次关系。

## s2.5 事件驱动对笔者的意义
每个程序员都是从顺序驱动开始学习的，轮询基本是在这个思维惯性下的必然。所以很多年前的一个晚上，笔者在看侯捷老师的《深入浅出MFC》中消息泵和事件驱动的篇章时那种醍醐灌顶的感觉，至今记忆犹新。后来笔者进入互联网行业，常年从事后端开发工作，日常和 消息/协议/通讯 打交道，逐渐对消息驱动有了更深的理解。

有个很有意思但很能说明问题的例子，比如一个玩家挂机，每小时产出一份收益。那么玩家离线后这份收益需要计算么？如果按照顺序处理的逻辑，应该每小时计算，但按照事件驱动原则，只有玩家下次上线时才需要计算。如果玩家不上线，这个事件永不触发。

手里有了锤子，看什么都是钉子（笑）。在笔者看来，微博、微信、小红书、淘宝，每一个热门网络服务背后，都有 **事件驱动** 和 **无状态服务** 的影子。事件驱动决定客户端访问的形式，无状态服务 让 动态扩容（这又是另一个话题了）等高阶技术成为可能。

## s2.6 回到 “事件驱动” 这个词
写到这里，笔者可以给出一个更具体的定义了：

事件驱动，在办事大厅里不是什么抽象概念，就是一套具体的规则：

叫号屏幕亮了，工作人员就处理当前这个人的材料。每个人按顺序来，一次只占一个窗口。窗口工作人员不需要记任何东西，材料本身携带所有必要信息。处理完了，交给下一个人。

对应到 Gaia 里就是：事件来了，Handler就执行。每个Handler是无状态的，所有状态都在 Context 里跟着请求走。同一连接一次只处理一个请求。执行完了，继续处理下一个事件。

这不是什么玄学，就是一层套一层的分工，加上一把严严实实的入口锁。剩下的，就是按照顺序逻辑把每一件事做好。

这也是为什么笔者在系列开头说，Gaia要让开发人员 *“接近零心智负担地使用并发线程能力”*——因为你根本不需要感知并发，它已经被门口的排队机制和窗口的无状态设计消化掉了。你只需要像办事大厅的工作人员一样，专注于处理眼前这一份材料就够了。
