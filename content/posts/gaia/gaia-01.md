## 0.1.1 缘起
笔者现供职于一家做机器视觉检测的公司。入职后发现，团队技术积累与业务需求之间存在较大差距，日常开发中遇到了一些技术上的挑战。

第一年，笔者的主要工作是基于原代码开发新需求。但是那套代码的痛点非常明显，首先没有成熟的通讯管理，只能以较为原始的方法，一个线程管理一个 socket，进行二进制数据的收发；其次基于 MFC框架，无法承载团队希望 *现代化一点* 的界面设计需求。笔者用 Qt 遮盖了原本的 MFC前端，简化了界面开发负担，同时用 *IOCP+Protobuf* 重构了通讯方案，并在此基础上设计了规范的消息分发和路由机制。在这个过程中，也对业务有了进一步的认识。

<!--more-->

第二年，项目从立项到预设的交期大概有3个月，在了解到团队没有 *必须死守这套代码* 的执念，并且评估时间来得及之后，笔者决定重新开发一套不需要背负技术债的代码。在这套代码中，笔者借用以前积累的开发经验，用自己曾经随手开发的小玩具（harborRPC，借鉴模仿云风的skynet）建立了一套线程间 rpc通讯 的方案，将原本纷乱的业务逻辑拆分成一个个独立的模块，并且拥有各自独立的线程。线程内部是 Actor模型，规避了竞争风险。这是笔者过去十多年开发经验在新领域的一次迁移尝试。并且用另一个小玩具（cometIOCP，一个带有 **协议注册** 的iocp封装）完善了通讯模块。基于这个代码构建的项目的稳定性得到了肯定，由其支撑的项目也得到了公司的年度嘉奖。

今年以来，公司基于我去年的代码，同时规划了多条产品线。因为各种原因，笔者只需要负责其中一个项目，其他项目完全交由其他同事跟进开发。这让笔者开始重新审视自己开发的代码，是否足够清晰简单，能支持任何水平的开发人员，简单而专注的开发自己的逻辑？答案是沮丧的，显然不行。因为很多代码逻辑没有摆脱历史代码的影响，耦合性仍然很高，仍然过于依赖开发人员的经验和能力。

在入职这家公司之前，笔者曾在上海知名游戏公司担任十多年主程。后来因为行业寒冬，以及个人原因，在团队解散后决定回老家，并转行入职这样一个搭边 AI 的公司。十多年来，笔者最擅长，也是一直在做的，就是开发稳定、可靠、对各种水平的开发人员都友好的框架。

于是，笔者决定利用这段相对轻松的时间，以 *高效开发* 和 *稳定运行* 为核心目标，重新开发一套框架。**Gaia framework** 于是逐渐成型。

## 0.1.2 致敬
Gaia framework 的风格，与笔者当前所在团队的既有代码截然不同，它源自笔者二十年开发经验的沉淀，源自开源社区众多项目对笔者的启发。**libevent**、**skynet** 等众多优秀的开源项目，是 **Gaia** 的根。后面笔者逐一介绍内部细节的时候，会再次提到，里面有多少东西，是对这些前辈的拙劣模仿。

## 0.1.3 Gaia是什么
**Gaia Ain't Industrial Automation**

Gaia致力于针对有多个边缘计算节点的工业场景，提供稳定可靠且易于开发的开发框架。开发人员不用操心设备管理、线程管理、通讯管理、会话管理等复杂的细节。

Gaia的特点：
* 声明式的 API 注册和专注于逻辑的 handler 实现
* 极致简单优雅的 send/call 语义
* 接近零心智负担的并发线程能力
* 对典型工业协议的抽象和隐藏
* 不预设任何业务逻辑，也不绑定特定硬件

开发人员只需要专注于业务逻辑，以及贴合业务的 driver 实现，即可快速利用 Gaia 搭建稳定可靠且支持多前端的后台服务。

## 0.1.4 术语
* 平台：即Gaia framework
* 3层架构：[ Driver层 ] <--> [ 平台层 ] <--> [ 业务层 ]
* Edge：边缘计算节点
* Equipment：机台设备
* Gateway：多前端接入网关
* API：Application Programming Interface，在 Gaia 里是一组 *元方法*，可以被前后端调用，也可以循环调用
* Manager：业务层可能需要这样一层，具体在Equipment模块会详细举例
* req|request：一次应答响应的起点，每个 req 都会对应 resp，哪怕是超时熔断后由系统生成的回复
* resp|response：和一个 req 形成一组完整的会话，使用同一个 session id 标识
* cmd|command：由 req——resp 对组成的完整会话
* notify：单方面事件通知，不需要回复
* 通信协议：Gaia framework 中的协议由 Req|Resp|Notify 共同组成
